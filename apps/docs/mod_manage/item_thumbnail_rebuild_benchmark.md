# 单物品缩略图重建抽样耗时（2026-10-02）

## 背景与调用路径

物品详情的“重建缩略图 → 从外部导入”调用 `import_zipmod_item_thumbnail()`。该操作读取目标 CSV，重写 zipmod（替换 CSV、加入 PNG），随后调用 `_replace_mod_items()` 重扫整个模组并更新索引。批量缩略图任务目前逐物品重复调用同一函数。用户希望知道对数据库物品操作的平均耗时，并使用原有物品缩略图做写回测试。

## 抽样和隔离

- 测试脚本：`apps/scripts/benchmark_item_thumbnail_rebuild.py`。读取现有 `apps/backend/runtime/star_manager.sqlite`，只纳入非 Studio、`parse_status=ok`、`thumbnail_status=ready`、原 zipmod 与缓存 PNG 均存在的物品，共 **38,261** 条。
- 为控制测试磁盘占用，抽样限定 zipmod ≤350 MiB，覆盖 **37,471/38,261（97.9%）** 的候选物品；>350 MiB 的 790 条不在本次均值内。将限定范围内的物品按 zipmod 大小分为十等份，每份固定随机种子抽 3 条，且每个 zipmod 最多 1 条，共 30 条。
- 每条样本先复制原 zipmod 到工作区临时目录，并在临时 SQLite 中建立对应 zipmod 与物品记录。调用真实的 `export_zipmod_item_thumbnail()` 从原有缓存导出 PNG，再调用真实的 `import_zipmod_item_thumbnail()` 写回副本。计时不含准备阶段的 zipmod 复制、临时库创建及事后校验。
- 校验写回 zipmod 中 PNG 的 SHA-256、CSV 新引用、重扫后的 `thumbnail_status=ready`，以及新缓存 PNG 的 SHA-256。原游戏 zipmod、运行时数据库和原缓存均未写入。
- 首轮 30 条中 29 条完成；1 条在 Windows 临时 zipmod 替换时返回 `WinError 5`，单独重试后通过全部校验。下表合并 29 条首轮成功值与该条重试值，每个物品计一次。这个失败提示替换阶段可能遭遇临时文件占用，但一次故障不足以推断发生率。

## 结果

| 阶段 | 30 条均值 | 说明 |
| --- | ---: | --- |
| 导出原缩略图 | 10.5 ms/物品 | 从已有缓存复制 PNG；不计入导入函数 |
| 单物品导入写回 | **326.0 ms/物品** | 真实函数端到端；中位数 197.5 ms，P90 709.0 ms，范围 18.9–1256.3 ms |
| 其中：zipmod 重写 | 42.8 ms（13.1%） | 保留原成员的压缩数据、替换 CSV、添加 PNG、原子替换归档 |
| 其中：整个模组重扫 | **243.5 ms（74.7%）** | 重新读取 CSV、提取/检查其它物品缩略图和资源状态、回写索引 |
| 其中：其它处理 | 39.7 ms（12.2%） | 输入/数据库查询、读取 manifest、更新和返回等 |

将导出与导入合计，均值约 **336.5 ms/物品**。最大包体分位（本次约 139.7–233.1 MiB 的 3 条）导入均值为 749.4 ms。样本中一个 155 MiB、1080 条物品的模组耗时 1256 ms；16.5 MiB 的重试样本也因重扫耗时 965 ms 而达到 1014 ms。这说明按包体单独预测不够，模组内物品数和缩略图引用结构也会改变耗时。

## 优化方案

1. **优先取消单项写回后的全模组重扫。** 写回前已知目标物品、CSV 和 PNG，写回后可只验证并解析该 CSV 的目标行，更新目标 `mod_items` 的 `thumb_ab`、`thumb_tex`、缓存路径和状态，并更新 `zipmods` 的大小与修改时间。其它物品行不必重新提取缩略图。仅在目标行不唯一、CSV 结构变化、写回校验失败等情况下回退到完整重扫。按本次阶段占比，完整消除重扫的理论均值上限约 243.5 ms/物品；这是阶段耗时上限，不能当作已验证的新实现耗时。
2. **批量任务按 zipmod 分组写回。** 目前 `bulk_apply_item_thumbnail` 每个物品调用一次单项导入，同一 zipmod 会被多次整体重写和重扫。先收集该包内目标 CSV/PNG 变更，再对该包做一次原子重写和一次必要的索引更新。需处理同一 CSV 中多目标行、重复 ID、单项失败隔离和任务进度。
3. **增强 Windows 替换阶段的恢复。** 对临时目标文件被短暂占用的 `PermissionError` 做有界重试，并明确报出目标路径与失败阶段；重试前保持原 zipmod 完整。此项主要提高稳定性，收益不是平均耗时。
4. **用同一 30 个样本做实现前后 A/B。** 分开报告导出、归档重写、索引更新、失败率及 >350 MiB 尾部包体；保留写回 PNG/CSV/缓存的逐项校验，避免用速度换掉正确性。

现有 `rewrite_zip_members()` 已原样复制未修改成员的压缩数据。本轮 74.7% 的耗时在重扫，因此当前优先级应放在索引更新范围，而不是再优化压缩算法。

## 证据与适用边界

原始结果位于未提交的 `apps/tmp/benchmark_item_thumbnail_rebuild_20261002.json` 和单条重试 `apps/tmp/benchmark_item_thumbnail_rebuild_retry12.json`。该测试使用现有缓存 PNG，代表“从外部导入”路线；不包含前端文件选择、HTTP 传输、3D 截图/模型加载，也不代表缺失缩略图、Studio 物品或 >350 MiB 的 zipmod。隔离副本所在目录没有原游戏的 `abdata`，所以外部游戏资源的状态检查可能比真实游戏目录更快，**326 ms 不是所有环境的保证值**。数据还受本机磁盘缓存、杀毒/文件占用、Python 运行时和现有模组结构影响。
