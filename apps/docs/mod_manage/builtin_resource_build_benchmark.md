# 原版资源索引建库性能基准

## 测试对象

本次测试针对 `builtin_database.build_builtin_items_index()`，不包含 zipmod 扫描和角色卡数据库。测试使用本机实际 HS2 目录：

```text
E:\game\HoneySelect 2 DX - TSYMQ
```

该目录包含 33 个 `abdata/list/characustom/*.unity3d` 列表包和 3 个 MapInfo 包。测试使用独立临时 SQLite、缩略图目录和 `mm_env` Python 环境，不覆盖应用运行时数据库或游戏文件。

测试脚本：[`apps/scripts/benchmark_builtin_index.py`](../../scripts/benchmark_builtin_index.py)。脚本对列表解析、地图 HPoint 扫描、缩略图提取、资源状态检查和源签名计算分别计时。

## 实测结果

| 场景 | 总耗时 | 原版条目 | 地图 | 缩略图成功 | 缩略图缺失 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次 incremental | 18.048 s | 1,703 | 27 | 1,537 | 166 |
| 首次 full | 17.172 s | 1,703 | 27 | 1,537 | 166 |
| 同进程缓存复用 | 0.005 s | 1,703 | 27 | 1,537 | 166 |

两次首次构建的差异来自文件系统缓存和机器负载；不能把 0.876 s 视为 full 模式的稳定收益。缓存复用命中 `builtin_index_ready`、游戏目录 key 和解析器版本后，不再读取 Unity3D 包。

### 阶段拆分

并发改造前首次 incremental 的计时如下，作为优化前基线：

| 阶段 | 调用次数 | 累计耗时 | 占首次总耗时 |
| --- | ---: | ---: | ---: |
| 原版缩略图提取 | 1,703 | 8.534 s | 47.3% |
| MapInfo + 场景 HPoint 扫描 | 3 个 MapInfo，43 个场景 | 8.008 s | 44.4% |
| 列表包 `ChaListData` 解析 | 33 | 0.209 s | 1.2% |
| 原版源签名计算 | 1,703 | 0.673 s | 3.7% |
| 原版资源状态检查 | 1,703 | 0.407 s | 2.3% |

阶段计时包含少量嵌套和数据库写入边界差异，因此各项不作为精确加总。结论很明确：缩略图提取和地图场景扫描合计约占 90% 以上；MessagePack 列表解析和 SQLite 单行写入不是主要瓶颈。

当前 `apps/backend/app/bridge.py` 的加权进度仍把原版资源索引按 2.5 秒历史基线计权。本次实测首次扫描约 17–18 秒，若用户执行的是首次原版索引，顶部进度会低估该阶段耗时；建议在完成更多机器上的重复样本后同步更新进度权重。

## 多线程优化实测

并行实现将 UnityPy 读取、MapInfo/HPoint 扫描和缩略图准备放到 worker，SQLite 仍由主线程提交。使用相同目录分别启动独立 Python 进程测量，避免进程内解析缓存影响结果：

| worker 数 | 首次构建耗时 | 与单线程相比 |
| ---: | ---: | ---: |
| 1 | 约 19.1 s | 基线 |
| 2 | 约 14.5 s | -24% |
| 4 | 约 13.3 s | -30% |
| 8 | 约 11.9 s | -38% |

另一次文件系统缓存较热的 1/4/8 worker 轮次分别为 17.3/12.9/11.9 秒，趋势一致。所有轮次均得到 1,703 条物品、27 张地图、1,537 张可用缩略图和 166 条缩略图缺失记录。

## 优化建议

### 1. 持久化场景 HPoint 元数据缓存（最高优先级）

当前 `_BUILTIN_SCENE_HPOINT_CACHE` 只存在于 Python 进程内。应用重启后，43 个场景会再次由 UnityPy 加载和遍历，单次约 7.6–8.0 秒。可以按“场景路径 + 文件大小 + mtime + 解析器版本”建立持久化缓存，保存 HPointList 数量、HPoint 数量、有效状态和预览根节点。未变化的场景只读缓存，变化或解析器升级时再扫描。

### 2. 将缩略图提取移出建库关键路径

1,703 个物品的缩略图提取约 8.1–8.5 秒，且 166 个物品最终没有可用缩略图。建议先写入物品和资源状态，再把缩略图提取作为后台阶段；前端可先显示稳定占位图，缩略图完成后刷新。这样不会减少总工作量，但能缩短数据库可用等待时间。

### 3. 继续评估受控并发的内存边界

当前实现已经使用受控线程池并行读取列表、场景和缩略图。8 worker 在本机约比单线程快 38%，但累计子计时显示 UnityPy 和图片处理会争用 CPU/磁盘；后续应在低端磁盘和较大内存压力下比较 4 与 8 worker，再决定是否允许用户单独调低并发度。

### 4. 持久化 Unity3D 缩略图包索引

`_BuiltinThumbnailBundleCache` 也是单次建库内存缓存。可按源文件签名持久化“包内对象名 → 路径/类型”索引，重复全量建库时跳过 UnityPy 包级枚举，只在签名变化时重建。图片 PNG 仍应按物品源签名失效，避免旧图误用。

### 5. 增加源目录签名，保持增量复用同时检测变化

当前已完成索引的同目录会快速复用。后续可额外保存列表包和 MapInfo 包的路径、大小、mtime 汇总签名：签名未变时保持毫秒级复用；签名变化时只重扫受影响的包和场景，避免为了正确性退回全量扫描。

## 适用边界

结果适用于本机 Windows、当前磁盘缓存状态、`mm_env` 的 UnityPy 版本和上述游戏目录。首次构建耗时会随磁盘类型、Unity3D 包内容、场景数量和缩略图资源分布变化；缓存复用结果代表当前实现的热路径，不代表首次扫描速度。建议后续优化仍使用同一目录，并至少重复 3 轮取中位数。
