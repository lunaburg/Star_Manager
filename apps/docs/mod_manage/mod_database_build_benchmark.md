# 模组数据库建库性能基准

## 测试背景

用户希望确认模组数据库构建过程中，压缩包读取/解压与 Unity3D 缩略图提取各自占用多少时间，并判断压缩包流程是否值得优化。本次测试直接使用现有运行时数据库
`apps/backend/runtime/star_manager.sqlite` 选择样本；源数据库和游戏目录中的模组文件均只读。

## 测试方法

- 数据库中有 10,630 条 `scan_status = ok` 的 zipmod 记录，且记录文件全部存在。
- 从这些记录按压缩包大小排序后分为 10 个等量区间，每个区间固定抽取 10 个，共 100 个不同模组；因此样本覆盖小、中、大包，而不是只抽取连续的 100 条记录。
- 100 个样本合计压缩包大小约 2,651.9 MB；平均 26.52 MB，中位数 10.98 MB；数据库中的物品记录合计 537 条。
- 使用独立临时 SQLite 和缩略图目录执行 3 轮完整建库，并执行 3 轮跳过“模组缩略图提取”但保留其它建库工作的对照组。
- 当前实现没有把 zipmod 完整解压到目录；“解压耗时”按 `zipfile` 从压缩包读取并解压被请求的成员计量。除 ZIP 读取外，UnityPy 容器加载和图片写出单独计量。
- 建库为 `mode = full`，100 个模组低于当前 100 个模组的单线程阈值；因此结果对应当前单线程建库路径。

## 实测结果

三轮的中位数如下，阶段时间来自 `build_database()`，缩略图差值来自完整组与对照组的配对比较：

| 指标 | 中位数 |
| --- | ---: |
| 完整建库总耗时 | 20.86 s |
| 跳过模组缩略图后的总耗时 | 10.29 s |
| 模组缩略图带来的总额外耗时 | 10.58 s |
| 完整建库中缩略图额外耗时占比 | 约 50.7% |
| 完整建库中 `item_parse` 阶段 | 11.01 s |
| `item_parse` 中缩略图额外耗时 | 10.75 s，约 97.6% |
| 非缩略图的模组解析/状态检查 | 约 0.26 s |
| SQLite 写入 | 约 0.01 s |

`build_database()` 还包含原版资源索引，三轮中位数约 9.53 s。它与模组压缩包及模组缩略图不是同一个耗时来源；如果用户看到的是整个“数据库构建”按钮耗时，原版资源索引也应单独考虑。

## 压缩包读取与缩略图内部拆分

对完整组的一轮做了 ZIP 成员级别计量。模组缩略图预提取阶段读取了 75 个 Unity3D 成员，累计约 2,567.0 MiB 的压缩包内容；逐物品备用读取另有约 25.1 MiB。对应的压缩包解压/读取 CPU 时间约 3.37 s。

按计时器累计值拆分：

| 子阶段 | 累计时间 | 说明 |
| --- | ---: | --- |
| ZIP 读取/解压（主要是缩略图 Unity3D） | 约 3.37 s | 读取 2.69 GB 压缩包成员；其中 2.57 GB 属于缩略图引用包 |
| UnityPy 加载 Unity3D 容器 | 约 4.97 s | 75 个模组缩略图 Unity3D 包；当前实现按包缓存 |
| 从已定位对象解码并写出 PNG | 约 1.41 s | 142 个模组缩略图写出 |
| 模组缩略图相关已计量子阶段 | 约 9.74 s | 另有约 0.7–0.8 s 用于引用分组、缓存判断和其它提取路径；与完整/对照组差值约 9.84 s 同量级 |

注意：测试同时计量了 1,514 个原版物品缩略图，它们在完整组和对照组中都会执行，所以不应计入上面的“模组缩略图额外耗时”。原版缩略图自身约为 0.6–0.7 s UnityPy 加载加 6.8–7.3 s 图片写出，属于另一个可优化方向。

样本中的缩略图 Unity3D 引用包分布也说明了压缩包大小问题：75 个被实际读取的引用包中，48 个为 ZIP 无压缩成员，27 个为 DEFLATE 成员；累计压缩大小约 1,339.8 MiB，解压后约 2,567.0 MiB。无压缩成员占被读数据约 69.4%，对它们不存在传统意义上的“减少 ZIP 解压计算”空间，主要成本是磁盘读取、内存复制和 UnityPy 解析。

## 是否存在优化空间

存在，而且第一优先级不是改 ZIP 算法，而是减少“不必要地读取和解析的大包”：

1. 当前每个模组会先执行 `preextract_zip_unity_thumbnails()`。只要 CSV 引用了某个 Unity3D 缩略图包，就会读取整个 ZIP 成员并让 UnityPy 建立容器索引；即使最终只需要其中一张图，也要承担包级加载成本。75 个包中有少数超大包贡献了主要读取量，例如样本中约 367 MiB、246 MiB、218 MiB、150 MiB 的引用包。应优先做按包/引用签名的持久化缩略图元数据缓存，命中后不再重复 ZIP 读取和 UnityPy 加载。
2. 当前 `thumbnail_cache_path` 只由 GUID、item、ThumbAB、ThumbTex 组成，缓存文件存在时单条路径可以命中；但完整 `full` 重建使用独立空目录，无法复用历史的 Unity3D 包解析结果。增加“源 zipmod 路径 + 文件大小 + mtime + ThumbAB”的持久化对象目录索引，可把重复全量重建的 UnityPy 包加载从建库主路径移出。
3. 已有“按目标读取”优化：`UnityThumbnailBundle` 只登记 container 路径和 `peek_name()`，匹配目标后才 `obj.read()`。因此继续优化“不要解码无关图片”已经做过，当前实测中剩余大头是 ZIP 读取与 UnityPy 包级加载，而不是无关纹理逐张解码。
4. 100 个模组当前走单线程路径。若产品允许把缩略图提取与数据库索引解耦，可在 I/O 和 UnityPy 可安全并发的前提下对独立 zipmod 做有限并发；但 Python 解码库、磁盘随机读取和内存峰值需要单独压测，不能直接把线程数调到 CPU 核数。
5. 对“首次打开数据库”体验，最有效的是把模组缩略图改为懒加载：先完成 CSV/资源状态入库，前端按可见分页异步提取缩略图，或将缩略图提取变成后台阶段。这样不能减少总工作量，但能显著缩短数据库可用时间。

## 当前结论

在这 100 个数据库真实样本上，模组缩略图流程约占完整建库墙钟时间的一半，且 `item_parse` 阶段几乎全部由它贡献。压缩包读取/解压本身约占模组缩略图额外耗时的 32%，UnityPy 包加载约占 53%，目标图片写出约占 13%（按本轮累计子计时计算，存在少量计时器与墙钟差异）。因此“压缩包是否可优化”的答案是：有空间，但单独替换 ZIP 解压算法的收益有限；应优先减少重复读取、持久化 Unity3D 结构索引、按需/懒加载缩略图，再评估受控并发。

## 验证产物与适用边界

本次原始结果保存在工作区临时目录的 `tmp/benchmark_mod_database_100_v3.json`，测试脚本为 `tmp/benchmark_mod_database_100.py`。临时 SQLite、缩略图和 profiling 文件均位于同名的 `tmp/benchmark_mod_database_100_v3_runtime/` 目录，不参与应用运行时数据库。

结论适用于当前机器、当前 Python/UnityPy 版本、当前磁盘缓存状态和这组按大小分层的 100 个样本。它不是所有模组库的精确预测；尤其是超大压缩包、无压缩 Unity3D、缩略图包内对象数量和磁盘类型都会改变比例。这里的 4.97 s / 1.41 s 是一次代表性完整轮次的模组缩略图子阶段计时，不包含同时发生的 1,514 个原版缩略图处理。

## GitHub 解压方案对比

### 候选方案

针对现有 zipmod 格式，实际相关的是 ZIP 的 Store（无压缩）和 Deflate 两种成员类型。GitHub 上考察了以下方案：

- [`pycompression/python-isal`](https://github.com/pycompression/python-isal)：Intel ISA-L 的 Python 绑定，提供与 `zlib` 兼容的 `isal_zlib`，可以在不改变 `zipfile` 调用方式的情况下替换 Deflate 解码器；本机通过 `conda install -n mm_env python-isal` 安装了 `python-isal 1.1.0` / `isa-l 2.30.0`。
- [`libarchive/libarchive`](https://github.com/libarchive/libarchive)：支持 ZIP，但主要优势是跨格式的 C 层流式归档访问；当前解析流程需要按成员随机读取并将指定 Unity3D 成员交给 UnityPy，引入 C 库/绑定后不一定比现有 `zipfile` 更快，因此未作为本轮直接替换方案。
- [`indygreg/python-zstandard`](https://github.com/indygreg/python-zstandard)：用于 Zstandard，不是现有 ZIP Deflate 的替代解码器；除非重新定义 zipmod 的压缩格式，否则不适用于当前文件。

### A/B 实测

使用与前一轮完全相同的 100 个模组、537 条物品、33 个原版资源包和 3 轮完整建库；每组在独立 Python 进程中运行。`isal` 只替换 `zipfile` 使用的 Deflate 解码模块，数据库逻辑、UnityPy 版本、缩略图输出和样本均不变。以下为完整建库的三轮中位数：

| 指标 | 当前方法：stdlib `zlib` | `python-isal` | 变化 |
| --- | ---: | ---: | ---: |
| 完整建库总耗时 | 19.89 s | 19.27 s | 减少 0.62 s（3.1%） |
| `item_parse` 阶段 | 10.62 s | 9.98 s | 减少 0.63 s（6.0%） |
| ZIP 成员读取/解压计时累计 | 3.31 s | 2.68 s | 减少 0.63 s（19.2%） |
| 其中 Unity3D ZIP 成员 | 3.25 s | 2.62 s | 减少 0.63 s（19.5%） |
| UnityPy 容器加载 | 5.79 s | 5.64 s | 减少 0.16 s（2.7%） |
| PNG 写出 | 7.84 s | 7.86 s | 基本不变 |

对照组（跳过模组缩略图）总耗时的中位数为 stdlib `zlib` 9.57 s、`isal` 9.62 s，差异约 0.05 s，说明两组的原版资源索引和数据库写入没有稳定变化；完整组的收益主要来自 Deflate 解码，而不是其它阶段。

### 结果解释与边界

`isal` 的 ZIP 读取计时下降约 19%，但完整建库只下降约 3%，原因是样本中实际读取的 Unity3D 内容约 69.4% 来自 ZIP Store 无压缩成员；这些数据不经过 Deflate 解码，替换 zlib 不会带来收益。同时，模组缩略图阶段还包含约 5.6–5.8 s 的 UnityPy 包加载和约 7.8 s 的 PNG 写出，它们也不会因更换 Deflate 解码器而明显缩短。

因此，`python-isal` 存在可测性能提升，适合作为低风险实验性优化：它可使当前这组样本的完整建库平均少约 0.6 s，但不足以解决缩略图建库耗时。正式接入前仍应在目标用户机器上验证 ISA-L 的 Windows 运行库、异常 ZIP、加密/损坏成员和不同磁盘类型；并在应用启动时优雅回退到标准库实现。

本轮实验脚本增加了 `--zip-backend stdlib|isal` 参数，原始结果分别保存在 `tmp/benchmark_mod_database_100_stdlib.json` 和 `tmp/benchmark_mod_database_100_isal.json`；它们属于工作区临时验证产物，不是应用运行时数据库。
